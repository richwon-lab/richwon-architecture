## 검토 방법

다음 제안은 작성자가 권장안을 채운 검토 대상입니다. 이미 확인된 핵심 요구인 사용 편의성, 직원의 업무 내용 편집, 자체 서버 장애 시 업무 지속, 서버 독립적인 공정 인계 자체를 다시 승인받기 위한 목록은 아닙니다.

각 항목에 ‘승인’, ‘수정 후 승인’, ‘보류’와 필요한 의견을 남깁니다. 예: `RV-03 승인`, `RV-02 서버와 앱은 하나의 구현 저장소로 수정`, `RV-06 참가자 수는 2명으로 조정`. 일부 항목만 먼저 검토할 수 있습니다.

RV-02 저장소 구성은 수정 후 승인되었습니다. RV-03~RV-12는 검토 대기입니다. 승인된 항목의 최종 결정은 이 목록에 남깁니다.

## 마일스톤과 검토 항목

프로젝트의 현재 단계와 다음 작업은 [프로젝트 마일스톤](../index.md#프로젝트-마일스톤)에서 확인합니다. RV는 검토 항목의 식별자입니다. 진행 중인 마일스톤에 필요한 결정부터 검토합니다.

- **첫 도입 범위 확정:** 대표 업무와 예외를 바탕으로 첫 도입 범위(RV-05)를 먼저 검토하고, 해당 도안 품질(RV-12), 사용성(RV-06), 편집 범위(RV-07), 장애 중 업무와 인계(RV-08) 기준을 구체화합니다.
- **아키텍처와 구현 경계 확정:** 합의된 업무·장애 시나리오에 맞춰 인증(RV-09)과 설치·업데이트 방향(RV-10)을 검토합니다.
- **프로젝트 운영:** 역할(RV-03), 문서 체계(RV-04), 단계 전환과 변경 관리(RV-11)는 적용이 필요한 시점에 검토합니다. RV-04에서는 공통 관리 저장소의 프로젝트 수준 항목과 구현 저장소의 상세 이슈를 링크로 연결하는 방식을 검토합니다. RV-11에서는 단계별 종료 증거, 확인 역할, 잔여 항목의 처리 기준을 검토합니다.

RV-05에서는 기존 디자인을 이용한 도안 자동화를 로컬에서 먼저 도입하는 안을 함께 비교합니다. 과거 작업 데이터와 고객별 기준을 여러 직원이 언제부터 공유해야 하는지, 생산 인계에 무엇이 필요한지 먼저 확인합니다. RV-08에서는 그 결과를 바탕으로 반드시 지속해야 할 개인 작업과 인계 범위를 구체화합니다. 단계별 검토를 유지하면서 작은 범위를 먼저 현장에 적용하는 방식은 RV-11에서 검토합니다.

- 검토일: 2026-11-21
- 검토자 역할: 프로젝트 요청자
- 결과: 수정 후 승인
- 최종 결정: `richwon-architecture`에서 공통 요구사항·아키텍처·연동 계약·프로젝트별 구현 항목을 관리한다. 아키텍처의 책임과 연동 경계에 따라 구현 프로젝트를 구분하고 각각 별도 저장소로 관리한다.
- 변경 이유: 각 구현 프로젝트의 작업 범위를 자체 저장소와 공통 관리 문서로 한정하고, 여러 구현 프로젝트의 연동 조건과 진행할 항목을 한곳에서 확인한다.
- 후속 결정: 구현 프로젝트의 수와 이름은 아키텍처 정의 후 결정한다. 원격 저장소의 공개 범위는 별도 검토한다.
- 반영 문서: README, DOC-OVERVIEW, DOC-GOV, DOC-INDEX.
- 반영 상태: 문서 반영 완료.
