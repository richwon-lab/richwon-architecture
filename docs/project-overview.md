# 프로젝트 개요

문서 ID: DOC-OVERVIEW · 상태: 검토 중 · 내용 책임: 제품 책임자 · 개정: 0.2 · 2026-11-21

## 1. 목적

R-edit은 리치원컴퍼니 직원이 명판 제작 업무에서 사용하는 정보·도안 기준·작업 자료를 다루고 다음 공정으로 인계하도록 지원하는 사내 업무 시스템입니다.

기능 수보다 직원이 업무를 이해하고 완료할 수 있는지를 우선합니다. 업무 정보와 규칙의 일상적인 변경이 개발자에게 집중되지 않도록 합니다. 자체 서버의 장애는 정상인 직원 PC 사이의 업무 진행과 자료 인계를 막지 않아야 합니다.

## 2. 업무 환경

업무의 전체 맥락은 견적, 발주, 도안, 생산, 마감, 포장, 납품과 검수입니다. 정확한 공정 경계와 검수 시점은 대표 작업의 실제 흐름으로 확인합니다.

고객 발주는 이메일로 수신하며 Google Drive를 파일 공유에 사용해왔습니다. 인터넷 장애는 이메일 수신 등 외부 업무도 제한합니다. 같은 공정 작업자끼리의 자료 공유는 드물지만 다음 공정으로 자료를 넘기는 과정은 업무 지속에 중요합니다.

기존 프로그램의 사용 여부와 장비 연결 방법은 연동 대상 조사에서 확인합니다. 모든 기존 도구를 교체하는 것을 프로젝트의 전제로 삼지 않습니다.

## 3. 사용자와 책임

> **검토 주석 RV-03:** 아래는 업무 분석을 위한 역할 분류안입니다. 실제 직원 직급이나 시스템 접근 권한을 확정한 표가 아닙니다. 한 사람이 여러 역할을 맡을 수 있습니다.

| 역할 | 주요 업무 | 설계 시 고려 |
| --- | --- | --- |
| 사무 담당자 | 주문 자료 확인·정리·업무 인계 | 컴퓨터·문서 작업 숙련도가 낮아도 수행 가능 |
| 도안·생산 담당자 | 제작 기준 확인·자료 준비·제작 단계 인계 | 실제 업무 도구와 파일 흐름 연속성 |
| 업무 설정 담당자 | 자재·업체·규칙·양식·매뉴얼 관리 | 개발 지식 없이 변경 가능, 영향 확인 |
| 시스템 운영 담당자 | 계정·배포·복구 관리 | 직원 PC 방문과 수동 운영 부담 최소화 |

‘업무 설정 담당자’가 모든 정보를 독점 편집한다는 의미는 아닙니다. 편집 대상별 권한은 업무 책임을 확인한 후 구분합니다.

## 4. 범위와 도입 방향

**장기 검토 범위:** 주문 자료에서 제작과 다음 공정 인계까지의 업무 지원, 고객별 제작 규칙, 템플릿, 업무 입력 항목, 매뉴얼, 제작·전송 설정 관리.

> **검토 주석 RV-05 · 초기 도입안:** 첫 도입은 ‘작업 자료 확인 → 작업 진행 → 다음 공정 인계’ 한 흐름을 우선 대상으로 제안합니다. 해당 흐름에 필요한 기초 정보의 편집 기능을 포함하고, 범용 템플릿 편집기·전체 CAD/CAM 대체·회계·급여 등은 첫 도입 범위에 넣지 않습니다. 이 제외는 영구적인 제품 제외가 아니라 초기 범위 제안입니다.

첫 도입에서 자료 탐색과 인계를 실제로 개선하고 사용성·서버 장애 조건을 확인한 뒤, 고객별 규칙과 편집 기능을 업무 중요도에 따라 확대하는 방향입니다. 단계적 도입은 요구사항·아키텍처를 먼저 검토한다는 진행 원칙과 함께 적용합니다.

편집 기능의 여섯 예시는 서비스 기능 수를 제한하지 않습니다. 필요 업무를 새로 발견하면 동일한 분류·검토 절차로 요구를 추가합니다.

## 5. 제품과 저장소 구성

제품명은 **R-edit(알에딧)**로 확정합니다. 기존 명판 자동화 프로그램의 이름을 이어가며 명판 관련 업무 전반으로 범위를 확장합니다.

공통 설계·관리는 `richwon-architecture`에서 맡습니다. 아키텍처에서 구성요소의 책임과 연동 경계를 정한 뒤, 해당 경계에 따라 구현 프로젝트를 구분하고 각각 별도 저장소로 관리합니다. 구현 저장소의 수와 이름은 그때 결정합니다.

공통 관리 저장소에 시스템 구성도, 프로젝트별 책임과 구현 항목, 관련 요구 ID, 연동 계약과 검증 조건을 둡니다. 연동 계약에는 데이터 형식, 정상·실패 시 동작과 호환 조건 등 양쪽이 알아야 할 내용을 기록합니다.

각 구현 프로젝트는 자체 코드·테스트·배포 설정을 관리합니다. 연동에 필요한 정보는 공통 관리 저장소에서 확인할 수 있어야 합니다. 연동 계약이 바뀌면 공통 문서와 영향을 받는 프로젝트별 구현 항목을 함께 갱신합니다. 원격 저장소 이름과 공개 범위는 별도 검토 사항입니다.

## 6. 설계 검토 방향

> **검토 주석 RV-10:** 설치형 앱을 기준으로 설계를 진행하고, 배포 방식은 직원이 설치 파일을 찾아 각 PC에서 수동 교체하지 않아도 되는 방식을 우선 검토합니다. 관리자가 배포 버전을 지정하고 앱에서 업데이트를 안내하며 작업 종료 후 적용하는 운영을 초안으로 제안합니다. 강제 적용·유예·실패 복구는 운영 설계에서 구체화합니다.

인증 등 공통 기능은 책임과 인터페이스를 명확히 나누되, 초기부터 물리적 서버를 분리하지 않는 방향을 제안합니다. 서버 장애 중 인증 만료·재시작 문제는 업무 연속성 시나리오와 함께 검토합니다.

언어·프레임워크·DB·전송 프로토콜은 아키텍처 단계의 비교 대상으로 둡니다. 빈칸으로 방치하는 대신 해당 단계에서 사용성, 서버 장애 대응, 기존 도구 연동, 유지보수 비용에 대한 대안 평가와 ADR을 산출합니다. 현재 문서 검토를 위해 기술 선택을 선행하지 않습니다.

서버 PC 구매는 본 문서의 검토 범위에서 제외합니다.

## 7. 성공 판단

제품의 성공은 합의된 대표 업무를 실제 직원이 수행하는지, 지원되는 업무 변경을 코드 수정 없이 처리하는지, 자체 서버 장애 중에도 합의된 업무와 인계를 지속하는지로 판단합니다.

각 항목의 시험 조건과 인수 기준은 개별 요구사항 문서에 연결합니다. 초기 제품 전체의 효율 개선율이나 생산성 수치는 현재 근거가 없으므로 목표로 선언하지 않습니다. 대표 업무 확인 단계에서 현재 소요 시간과 오류 사례를 수집한 후 개선 목표를 추가합니다.
