# 프로젝트 개요

문서 ID: DOC-OVERVIEW · 상태: 검토 중 · 내용 책임: 제품 책임자 · 개정: 0.2 · 2026-11-21

## 1. 목적

R-edit은 리치원컴퍼니의 명판 도안과 제작 업무를 지원하는 사내 업무 시스템입니다. 기존 도안 자동화 이후에도 남아 있는 줄바꿈과 글자 폭 보정 같은 반복 작업을 줄이고, 생산 담당자에게 필요한 자료를 전달할 수 있도록 돕습니다.

컴퓨터 사용 경험이 거의 없는 직원도 처음 맡은 업무를 이해하고 스스로 완료할 수 있어야 합니다. 직원은 고객별 작업·검사 규칙을 코드 수정이나 프로그램 재배포 없이 관리할 수 있어야 합니다.

첫 도입에서 도안 자동화와 자료 인계를 어디까지 지원할지, 서버 장애 중 어떤 작업과 인계를 유지해야 할지는 [초기 검토 목록](reviews/initial-review.md)의 RV-05와 RV-08에서 검토합니다.

## 2. 업무 환경

명판 제작은 고객의 주문 자료를 바탕으로 도안을 준비하고 생산과 후공정으로 이어지는 업무입니다. 도안 담당자가 생산 담당자에게 넘기는 주요 자료는 도안 파일과 작업지시서입니다. 단계별 작업과 확인 지점은 [현재 업무 흐름](business/current-workflow.md)에 정리합니다.

주문 자료는 이메일을 비롯한 여러 경로로 들어옵니다. 기존 업무 기록에는 파일 공유에 Google Drive를 사용한 사례와, 기존 R-edit의 도안을 Type3에서 마무리하는 작업 흐름이 있습니다.

현재 사용하는 공유 경로와 도구, 생산 담당자가 작업을 시작할 때 필요한 자료, 장비 연결 방식은 연동 범위를 정할 때 확인합니다. 확인 항목은 [대표 업무와 예외](business/scenarios.md)에 정리합니다.

## 3. 사용자와 책임

아래는 [대표 업무와 예외](business/scenarios.md)에 기록된 작업을 역할별로 묶은 것입니다. 역할은 맡은 작업을 가리키며, 한 직원이 주문 확인과 도안을 함께 맡는 등 여러 역할을 수행할 수 있습니다.

| 업무 역할 | 맡는 일 |
| --- | --- |
| 주문 확인 | 고객 발주와 첨부 자료를 확인하고, 빠진 제작 조건을 확인합니다. |
| 도안 | 고객별 제작 기준에 맞춰 도안을 준비하고, 문구·수량을 확인한 뒤 도안 파일과 작업지시서를 생산에 넘깁니다. |
| 생산 | 도안과 작업지시서를 받아 자재를 준비하고 명판을 가공합니다. |
| 후공정 | 주문 조건에 맞춰 마감·포장·납품을 진행합니다. 세부 담당과 완료 조건은 업무 시나리오에서 확인합니다. |

고객별 규칙 등 업무 설정의 편집 권한은 실제 업무 책임을 확인해 정합니다. 계정·배포·복구에 필요한 운영 책임은 도입 방식과 함께 구체화합니다.

> **검토 주석 RV-03 · 프로젝트 역할:** 제품 책임자와 개발 담당자의 책임 구분, 한 사람이 두 역할을 맡는 방식, 실제 직원의 사용성 평가 참여는 [초기 검토 목록](reviews/initial-review.md)에서 검토합니다.

## 4. 범위와 도입 방향

### 장기 검토 범위

주문 자료 확인부터 도안·제작·공정 간 인계까지의 업무 지원을 검토합니다. 고객별 제작 규칙, 템플릿, 업무 입력 항목, 매뉴얼, 제작·전송 설정도 장기 검토 대상입니다. 도안 업무에서는 기존 자동화 이후에 남은 줄바꿈과 글자 폭 보정, 반복 주문의 결과 편차를 개선하고자 합니다.

### 첫 도입 후보

> **검토 주석 RV-05 · 검토 대기:** 첫 도입 범위와 도입 방식은 [초기 검토 목록](reviews/initial-review.md)의 RV-05에서 결정합니다.

- **도안 자동화 우선** — 기존 디자인을 이용하는 도안 작업의 수동 보정을 줄입니다. 한 대의 PC에서 로컬로 먼저 도입하는 방식도 이 후보에서 검토합니다.
- **자료 확인·인계 우선** — 작업 자료를 찾고 다음 담당자에게 전달하는 흐름을 개선합니다.
- **도안과 인계의 제한적 결합** — 기존 디자인의 도안 자동화와 생산 담당자에게 자료를 넘기는 부분을 함께 개선합니다.

[대표 업무와 예외](business/scenarios.md)를 기준으로 각 후보를 비교하고, 과거 작업 데이터와 고객별 기준을 언제부터 공유해야 하는지, 생산 담당자에게 어떤 자료를 넘겨야 하는지 확인합니다. 첫 도입에 필요한 기초 정보 편집과 후속 공정·도구의 범위도 이때 검토합니다.

첫 도입의 인수 기준은 선택한 업무에 맞춰 정합니다. 도안을 포함하면 [도안 자동화 요구 후보](requirements/design-automation.md)의 원문·수량·형상 보존, Type3 결과의 정확성, 수동 보정 부담을 살핍니다. 직원의 독립 수행은 공통 핵심 요구사항으로 적용하고, 장애 중 유지할 업무와 인계 범위는 RV-08에서 검토합니다.

## 5. 저장소 구성

저장소별 관리 대상은 [README의 ‘저장소의 역할’](../README.md#저장소의-역할)에서 확인합니다. 구현 프로젝트의 경계는 시스템 설계에서 구성요소별 책임과 서로 주고받는 데이터를 정한 뒤 결정합니다. 구현 저장소의 수와 이름은 그 경계에 따라 정합니다.

공통 설계에는 시스템 구성도, 프로젝트별 책임과 구현 항목, 관련 요구 ID, 연동 계약과 검증 조건을 기록합니다. 연동 계약에는 참여 프로젝트가 알아야 할 데이터 형식, 정상·실패 시 동작, 호환 조건을 명시합니다. 각 프로젝트는 자체 저장소와 공통 설계 문서를 바탕으로 연동을 구현하고 검증할 수 있어야 합니다.

연동 계약이 바뀌면 공통 설계 문서와 영향을 받는 프로젝트별 구현 항목을 함께 갱신합니다. 구현 저장소의 공개 범위는 별도로 검토합니다.

## 6. 설계 검토 방향

도입 방식은 첫 도입 범위(RV-05)를 바탕으로 비교합니다. 로컬 우선안에서는 한 대의 PC에서 합의된 도안 작업을 끝낼 수 있는지 확인합니다. 과거 작업 데이터와 고객별 기준을 여러 직원이 공유하거나 생산 자료를 전달해야 할 때는 그 요구를 바탕으로 서버의 필요성과 역할을 검토합니다.

> **검토 주석 RV-10 · 검토 대기:** 설치형 앱은 도입 후보입니다. 설치형을 선택한다면 직원의 수동 교체 부담을 줄이는 방법을 비교합니다. 관리자가 배포 버전을 지정하고 앱이 작업 종료 후 업데이트를 적용하는 방식은 검토안이며, 적용 시점·유예·실패 복구는 운영 설계에서 구체화합니다.

[README의 공통 설계 원칙](../README.md#공통-설계-원칙)에 따라 구성요소의 책임과 연결 방식을 명확히 합니다. 이후 데이터 공유나 인계를 추가할 때 수정할 부분과 검증할 기존 동작을 파악할 수 있는지 확인합니다. 인증에 서버가 필요하다면, 서버 장애 중 인증 만료와 앱 재시작의 영향을 합의된 업무 연속성 시나리오로 검토합니다.

아키텍처 단계에서 사용성, 기존 도구와의 연동, 첫 도입에 적용되는 장애 대응, 유지보수 부담을 기준으로 구조와 기술 대안을 비교하고, 주요 선택과 근거를 설계 결정 기록(ADR)에 남깁니다.

## 7. 성공 판단

첫 도입의 성과는 합의한 대표 업무를 실제 직원이 수행하는 과정과 결과로 판단합니다.

- **직원의 독립 수행(UX-001)** — 컴퓨터 사용 경험이 거의 없고 해당 업무를 처음 맡는 직원이, 다른 사람이 화면에서 할 일을 하나씩 알려주지 않아도 업무를 이해하고 올바른 결과까지 완료하는지 관찰합니다. 완료 여부, 도움 요청, 오류를 기록합니다. [사용성 요구사항](requirements/usability.md#ux-001--일반-직원의-독립적인-업무-수행)
- **직원의 고객별 규칙 관리(CFG-001)** — 직원이 화면에서 작업·검사 방식을 선택하고 고객별 적용 조건을 추가하거나 바꿉니다. 코드 수정이나 재배포 없이 같은 버전의 프로그램에서 해당 고객 작업에 의도한 결과가 반영되는지 확인합니다. [업무 설정 및 편집 요구사항](requirements/configuration.md#cfg-001--개발-변경-없는-업무-내용-편집)

도안 품질과 자료 인계는 첫 도입에 포함하기로 합의한 범위에 따라 평가합니다(RV-05). 서버 장애 대응은 RV-08에서 유지할 업무와 인계 범위에 합의한 뒤 해당 범위를 검증합니다. 시험 조건과 합격 기준은 관련 요구사항 문서에 기록합니다. 소요 시간과 오류는 현재 업무의 기준선을 먼저 측정한 뒤 개선 목표를 정하는 데 사용합니다.
