# 프로젝트 개요

문서 ID: DOC-OVERVIEW · 상태: 검토 중 · 내용 책임: 제품 책임자 · 개정: 0.2 · 2026-11-21

## 1. 목적

R-edit은 리치원컴퍼니의 명판 도안과 제작 업무를 지원하는 사내 업무 시스템입니다. 기존 도안 자동화 이후에도 남아 있는 줄바꿈과 글자 폭 보정 같은 반복 작업을 줄이고, 생산 담당자에게 필요한 자료를 전달할 수 있도록 돕습니다.

컴퓨터 사용 경험이 거의 없는 직원도 처음 맡은 업무를 이해하고 스스로 완료할 수 있어야 합니다. 직원은 고객별 작업·검사 규칙을 코드 수정이나 프로그램 재배포 없이 관리할 수 있어야 합니다.

첫 도입에서 도안 자동화와 자료 인계를 어디까지 지원할지, 서버 장애 중 어떤 작업과 인계를 유지해야 할지는 [초기 검토 목록](reviews/initial-review.md)의 RV-05와 RV-08에서 검토합니다.

## 2. 업무 환경

명판 제작은 고객의 주문 자료를 바탕으로 도안을 준비하고 생산과 후공정으로 이어지는 업무입니다. 도안 담당자가 생산 담당자에게 넘기는 주요 자료는 도안 파일과 작업지시서입니다. 단계별 작업과 확인 지점은 [현재 업무 흐름](business/current-workflow.md)에 정리합니다.

주문 자료는 이메일을 비롯한 여러 경로로 들어옵니다. 기존 업무 기록에는 파일 공유에 Google Drive를 사용한 사례와, 기존 R-edit의 도안을 Type3에서 마무리하는 작업 흐름이 있습니다.

현재 사용하는 공유 경로와 도구, 생산 담당자가 작업을 시작할 때 필요한 자료, 장비 연결 방식은 연동 범위를 정할 때 확인합니다. 확인 항목은 [대표 업무와 예외](business/scenarios.md)에 정리합니다.

## 3. 사용자와 책임

아래는 [대표 업무와 예외](business/scenarios.md)에 기록된 작업을 역할별로 묶은 것입니다. 역할은 맡은 작업을 가리키며, 한 직원이 주문 확인과 도안을 함께 맡는 등 여러 역할을 수행할 수 있습니다.

| 업무 역할 | 맡는 일 |
| --- | --- |
| 주문 확인 | 고객 발주와 첨부 자료를 확인하고, 빠진 제작 조건을 확인합니다. |
| 도안 | 고객별 제작 기준에 맞춰 도안을 준비하고, 문구·수량을 확인한 뒤 도안 파일과 작업지시서를 생산에 넘깁니다. |
| 생산 | 도안과 작업지시서를 받아 자재를 준비하고 명판을 가공합니다. |
| 후공정 | 주문 조건에 맞춰 마감·포장·납품을 진행합니다. 세부 담당과 완료 조건은 업무 시나리오에서 확인합니다. |

고객별 규칙 등 업무 설정의 편집 권한은 실제 업무 책임을 확인해 정합니다. 계정·배포·복구에 필요한 운영 책임은 도입 방식과 함께 구체화합니다.

> **검토 주석 RV-03 · 프로젝트 역할:** 제품 책임자와 개발 담당자의 책임 구분, 한 사람이 두 역할을 맡는 방식, 실제 직원의 사용성 평가 참여는 [초기 검토 목록](reviews/initial-review.md)에서 검토합니다.

## 4. 범위와 도입 방향

**장기 검토 범위:** 주문 자료에서 제작과 다음 공정 인계까지의 업무 지원, 고객별 제작 규칙, 템플릿, 업무 입력 항목, 매뉴얼, 제작·전송 설정 관리.

기존 R-edit의 도안 자동화에서 남은 줄바꿈·자폭 보정과 반복 주문의 결과 편차도 개선 대상이다. 첫 도입 범위 비교에는 [대표 업무와 예외](business/scenarios.md)와 [도안 자동화 요구 후보](requirements/design-automation.md)를 사용한다.

> **검토 주석 RV-05 · 초기 도입 범위:** 기존 자료 확인·인계 우선안, 도안 자동화 우선안, 기존 디자인의 도안 자동화와 생산 인계를 묶는 제한 결합안을 비교합니다. 기초 정보 편집과 후속 공정·도구의 범위도 첫 개선 목표를 결정할 때 함께 정합니다.

첫 도입의 성과는 합의한 대표 업무에서 평가합니다. 도안을 포함할 경우 원문·수량·형상과 Type3 결과의 정확성, 수동 보정 부담을 함께 평가합니다. 직원의 독립 수행과 자체 서버 장애 중 합의된 업무를 지속하는 기준은 관련 요구사항에서 관리합니다.

편집 기능의 여섯 예시는 서비스 기능 수를 제한하지 않습니다. 필요 업무를 새로 발견하면 동일한 분류·검토 절차로 요구를 추가합니다.

## 5. 저장소 구성

공통 설계·관리는 `richwon-architecture`에서 맡습니다. 아키텍처에서 구성요소의 책임과 연동 경계를 정한 뒤, 해당 경계에 따라 구현 프로젝트를 구분하고 각각 별도 저장소로 관리합니다. 구현 저장소의 수와 이름은 그때 결정합니다.

공통 관리 저장소에 시스템 구성도, 프로젝트별 책임과 구현 항목, 관련 요구 ID, 연동 계약과 검증 조건을 둡니다. 연동 계약에는 데이터 형식, 정상·실패 시 동작과 호환 조건 등 양쪽이 알아야 할 내용을 기록합니다.

각 구현 프로젝트는 자체 코드·테스트·배포 설정을 관리합니다. 연동에 필요한 정보는 공통 관리 저장소에서 확인할 수 있어야 합니다. 연동 계약이 바뀌면 공통 문서와 영향을 받는 프로젝트별 구현 항목을 함께 갱신합니다. 원격 저장소 이름과 공개 범위는 별도 검토 사항입니다.

## 6. 설계 검토 방향

> **검토 주석 RV-10:** 설치형 앱을 기준으로 설계를 진행하고, 배포 방식은 직원이 설치 파일을 찾아 각 PC에서 수동 교체하지 않아도 되는 방식을 우선 검토합니다. 관리자가 배포 버전을 지정하고 앱에서 업데이트를 안내하며 작업 종료 후 적용하는 운영을 초안으로 제안합니다. 강제 적용·유예·실패 복구는 운영 설계에서 구체화합니다.

인증 등 공통 기능은 책임과 인터페이스를 명확히 나누되, 초기부터 물리적 서버를 분리하지 않는 방향을 제안합니다. 서버 장애 중 인증 만료·재시작 문제는 업무 연속성 시나리오와 함께 검토합니다.

언어·프레임워크·DB·전송 프로토콜은 아키텍처 단계의 비교 대상으로 둡니다. 빈칸으로 방치하는 대신 해당 단계에서 사용성, 서버 장애 대응, 기존 도구 연동, 유지보수 비용에 대한 대안 평가와 ADR을 산출합니다. 현재 문서 검토를 위해 기술 선택을 선행하지 않습니다.

서버 PC 구매는 본 문서의 검토 범위에서 제외합니다.

## 7. 성공 판단

제품의 성공은 합의된 대표 업무를 실제 직원이 수행하는지, 지원되는 업무 변경을 코드 수정 없이 처리하는지, 자체 서버 장애 중에도 합의된 업무와 인계를 지속하는지로 판단합니다.

각 항목의 시험 조건과 인수 기준은 개별 요구사항 문서에 연결합니다. 초기 제품 전체의 효율 개선율이나 생산성 수치는 현재 근거가 없으므로 목표로 선언하지 않습니다. 대표 업무 확인 단계에서 현재 소요 시간과 오류 사례를 수집한 후 개선 목표를 추가합니다.
