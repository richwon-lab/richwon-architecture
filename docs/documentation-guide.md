# 문서 관리 규칙

문서 ID: DOC-GOV · 상태: 검토 중 · 내용 책임: 개발 담당자 · 개정: 0.1 · 2026-11-21

> **검토 주석 RV-04:** 이 문서 전체는 프로젝트 규모에 맞춘 관리 규칙 제안입니다. 특정 산업 표준 전체의 준수를 주장하지 않습니다. RV-03은 역할, RV-11은 단계 전환과 변경 관리에 대한 검토 항목입니다.

## 1. 문서 구성

README는 소개와 진입 경로를 제공합니다. 문서 목록은 실제 파일과 상태를 관리합니다. 개요는 목적과 범위를, 요구사항은 필요한 동작과 품질을, 설계는 이를 실현하는 구조를 설명합니다. ADR은 중요한 선택의 이유와 대안을 기록합니다.

요구사항은 주제별 파일로 나눕니다. 여러 업무에 공통인 사용성·연속성은 공통 명세로 유지하고, 주문·도안·제작 등 업무 기능은 범위가 구체화될 때 별도 명세로 추가합니다. 전체 내용을 단일 requirements.md에 누적하지 않습니다.

다음 중 하나에 해당하면 분리를 검토합니다: 독립적으로 검토·승인할 업무가 섞임, 변경 책임이 다름, 다른 문서가 특정 부분만 반복 참조함, 한 변경의 영향 범위를 파악하기 어려움. 줄 수만으로 분리하거나 요구 하나마다 파일을 만들지 않습니다.

## 2. 식별자와 문서 목록

- 문서 ID는 문서의 역할을 나타냅니다. 예: `SRS-USABILITY`.
- 요구 ID는 영역과 번호를 사용합니다. 예: `UX-001`, `CFG-001`, `BCP-001`.
- 요구 ID는 파일 이동 후에도 유지하며 폐기된 ID를 재사용하지 않습니다.
- ADR은 작성 시 `ADR-0001`부터 부여합니다. 결정 전 상태는 ‘제안’, 선택 후 ‘승인’, 대체 시 ‘대체됨’으로 관리합니다.
- 검토 의견에는 `RV-xx` 형식의 ID를 사용합니다. 제품 요구 ID와 혼용하지 않으며 이전에 사용한 ID는 재사용하지 않습니다.

문서 목록에는 ID, 링크, 목적, 상태, 내용 책임을 기록합니다. 날짜·상세 변경 내용을 목록에 중복하지 않습니다. 실제 변경 내용은 Git diff와 검토·결정 기록에 남깁니다.

## 3. 문서 상태와 버전

| 상태 | 의미 |
| --- | --- |
| 초안 | 작성 중이며 검토 요청 전 |
| 검토 중 | 제안이 채워져 있으며 검토·수정이 필요한 상태 |
| 승인 | 명시적 결정이 기록되어 해당 범위의 작업 기준이 된 상태 |
| 대체됨 | 후속 문서 또는 결정으로 대체되며 참조 경로를 유지 |

문서 상태와 구현·시험 상태는 별도로 관리합니다. 승인된 요구도 아직 구현되지 않을 수 있습니다.

초기 문서는 0.1로 시작하고 최초 승인 시 1.0으로 표시합니다. 편집 이력은 Git으로 관리하고 승인 기준점에는 관련 커밋을 기록합니다. 모든 오탈자 수정 때 별도 변경 이력 표를 늘리지 않습니다.

## 4. 요구사항 작성

각 요구에는 ID, 제목, 상태, 요구 본문, 업무상 이유, 적용 조건, 인수 기준, 관련 요구를 기록합니다. 요구 본문은 필요한 결과를 서술하고 구현 수단을 불필요하게 고정하지 않습니다.

근거는 업무 목적·운영 제약·정책·설계 결정으로 설명합니다. 대화 인용이나 ‘사용자가 말했다’는 표현을 업무 명세 본문에 넣지 않습니다. 결정의 확인은 검토 기록에 승인자 역할·날짜·대상 ID·결과를 기록하여 남깁니다. 전체 채팅의 보관을 전제로 하지 않습니다.

핵심 요구가 확인되었으나 세부 조건을 새로 제안하는 경우 두 상태를 구분합니다. 인수 기준을 시험하지 않고 ‘검증 완료’라고 기록하지 않습니다.

## 5. 검토 주석과 승인 처리

검토가 필요한 제안 바로 옆에 `검토 주석 RV-xx` 블록을 둡니다. Markdown 미리보기에서 보이지 않는 HTML 주석은 사용하지 않습니다.

초기 검토 목록에서 제안 요약, 영향 문서, 권장 이유와 결정 결과를 관리합니다. 검토자는 ‘승인’, ‘수정 후 승인’, ‘보류’로 의견을 남길 수 있습니다. 단순히 다음 작업을 진행하라는 말은 모든 제안의 승인으로 해석하지 않습니다.

승인 후 본문에는 확정 내용을 반영하고 임시 검토 주석을 제거합니다. 검토 목록에는 승인일, 승인 역할, 최종 결정, 관련 문서 ID를 남깁니다. 변경된 설계 결정은 기존 기록을 지우지 않고 대체 관계를 남깁니다.

## 6. 변경 절차와 추적

1. 문제와 변경 대상 ID를 기록합니다.
2. 영향받는 요구·설계·운영·검증 항목을 확인합니다.
3. 관련 문서를 함께 수정합니다. 범위 밖의 문서를 임의로 재구성하지 않습니다.
4. 링크, ID, 상태와 충돌 여부를 확인합니다.
5. 업무 범위·권한·합격 기준 등 실질적인 변경은 제품 책임자와 확인합니다. 의미를 바꾸지 않는 편집은 개발 담당자가 반영합니다.
6. 작업 단위로 커밋하고 현재 작업 상태를 갱신합니다.

RV-02에 따라 프로젝트별 구현 항목과 연동 계약은 공통 관리 저장소에서 관리합니다. 각 구현 프로젝트가 자체 저장소와 공통 관리 문서로 작업할 수 있도록 연동에 필요한 조건과 변경 영향을 공통 문서에 기록합니다.

변경 추적 방식으로는 구현 변경 설명에 관련 요구 ID와 설계 문서의 경로·기준 커밋을, 시험 결과에 검증한 요구 ID와 실행 조건을 기록하는 방식을 제안합니다. 요구 → 설계 → 구현 → 검증의 연결을 유지하되 아직 존재하지 않는 링크는 만들지 않습니다.

변경 요청은 관련 문서의 검토 항목으로 관리하다가 건수가 늘면 이슈 관리 도구를 사용합니다. 초기부터 모든 편집에 PR·다중 승인 절차를 강제하지 않습니다. 여러 사람이 병행 작업할 때 브랜치·PR 규칙을 추가합니다.

## 7. 단계별 검토

| 단계 | 종료 시 확인 |
| --- | --- |
| 요구사항 정의 | 사용자·대표 업무·첫 범위·핵심 품질 기준과 주요 예외가 설명되는가 |
| 아키텍처 | 책임·연결·자료 저장·인증·배포·장애 흐름이 핵심 요구를 충족하는가 |
| 상세 설계 | 화면·데이터·인터페이스·실패 처리와 시험 조건이 구현 가능한 수준인가 |
| 구현·검증 | 관련 요구의 인수 기준을 만족하며 실패 항목이 식별되는가 |
| 도입 | 직원의 업무 수행과 설치·업데이트·복구를 실제 환경에서 확인했는가 |

필요 시 기술적 불확실성을 확인하는 제한된 실험을 제안할 수 있습니다. 실험 결과는 제품 구현 완료로 처리하지 않습니다. 단계 전환 시 제품 책임자와 범위·잔여 위험을 확인합니다.

## 8. 작업 인수인계

작업을 마칠 때 문서 목록의 현재 작업에 단계, 완료 항목, 다음 작업과 보류 항목을 갱신합니다. 새 담당자는 문서 목록과 관련 검토·결정 기록으로 재개할 수 있어야 합니다.

인수인계에 개인 PC 폴더 경로, AI 대화 경위 또는 삭제된 파일을 알고 있어야 한다는 전제를 넣지 않습니다. 재현에 필요한 환경 정보는 향후 개발·운영 문서에 목적과 함께 기록합니다.

## 9. 문서 점검표

- **목적과 위치** — 누가 어떤 업무나 결정을 위해 이 문서를 쓰는가? 같은 정보의 기준 문서가 있다면 링크로 찾을 수 있는가?
- **용어와 사용성** — 현장에서 쓰는 말로 뜻이 분명한가? 제품 동작이나 합격 조건을 다루는 문서라면 컴퓨터 사용 경험이 거의 없는 직원도 담당 업무를 스스로 마칠 수 있다는 전제가 드러나는가?
- **상태와 근거** — 현재 사실, 제안, 승인된 결정, 시험 결과가 구분되는가? 주요 판단의 이유와 증거를 저장소에서 찾을 수 있는가?
- **인수인계** — 처음 온 담당자가 이전 대화 없이 현재 위치, 남은 결정, 다음 행동과 완료 기준을 찾을 수 있는가?
